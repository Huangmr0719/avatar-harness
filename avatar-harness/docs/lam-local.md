## 聆听反馈与快捷调节（2026-10-31，本地候选）

输入 `/` 弹出十个选项：自动、基础七类、认真、关切；支持搜索、键盘选择、Esc 收起及中文输入法。选择直接切换本地表情，其他命令保留原发送路径。生产页面的“部位调节”包含 52 项面部入口及头部三方向，当前形象为 51 项面部加 3 个头部方向可用。手动视线优先于相机视线控制，关闭面板、恢复自动或切换角色时释放覆盖。

本轮 64 项前端测试、类型检查/构建、Go 全量 race 和二进制构建通过。Chromium 1440×1000 与 1280×800 实测菜单、中文输入法、普通命令兼容、全部分组和调节恢复；头部转向约 20.8°，关闭覆盖后回到约 0.8°，没有跨帧累积。已有录音通过浏览器麦克风和真实 VAD 触发聆听、视线与点头，手动视线优先和结束聆听后的退出均通过；识别 WebSocket 使用本地模拟，未重新调用云端推理，不是物理麦克风端到端验收。无新增应用错误；底层渲染器保留正常的视线诊断日志。

## 历史：本地 WASM 方案与验证


浏览器使用 `@myned-ai/gsplat-flame-avatar-renderer@1.4.0` 渲染 LAM 高斯资产。语音推理使用 `onnxruntime-web@1.23.2`，在独立 Worker 的 WASM 中运行，模型、运行时和资产全部从当前 Go 服务读取，无运行时 CDN 请求，不需要 Python 或 CUDA 服务。

对话、ASR、TTS 仍走已配置的百炼；密钥只在 Go 服务端使用。`avatar` provider 可以保持 `deferred`，因为当前语音驱动在浏览器执行。页面“驱动就绪”来自实际模型加载和预热，不能用 provider 的配置状态替代。

## 真实语音与同步

百炼 PCM 包先合并为约 400ms，大包分块并限制每块最多 500ms，避免首个音频块触发多次推理后才起播；短尾等 70ms 后刷新；采样率变化或 PTS 不连续时不合并。音频重采样到单声道 16kHz，以滚动 1 秒上下文推理，只取新增音频对应的后缀帧。面部帧生成后，音频进入 AudioContext 排程，动作依照实际排程 PTS 读取。

停止／插话会取消播放、清空待合并 PCM、重置上下文和动作时间线；已在运行的 WASM 算子会完成，但其过期结果不能重新启动声音。音频结束后恢复闭口待机。

表情默认自动：同一次 LLM 回复输出紧凑 JSON，包含 `emotion`、`intensity`、`speech`，后端流式解析后分别下发表情事件与正文。正文开始提交后即可驱动 TTS，不等待整份 JSON 结束，不额外调用一次 LLM，也不增加工具往返回合。需要外部工具时继续走原生 tool_calls，工具结果后的最终回复再输出上述 JSON。

页面显示“自动 · 当前表情”，可手动预览中性、快乐、悲伤、愤怒、恐惧、惊讶、厌恶，并兼容认真、关切交流风格；再选择自动即可恢复控制。自动表情默认保持 8 秒，实际播放超过该时长时延长至已排程音频结束后 250ms；停止、插话或新会话会清除旧轮状态。重放历史和迟到结果不能改变当前表情。强度与样式均检查范围，参数本身不混入日志正文或 TTS 播报文本；TTS 以独立指令使用同一份情感。

### 整脸驱动的职责与限制

当前社区音频模型不能仅凭“输出 52 维”称为有效整脸表情模型。三段同文本情感语音的实际浏览器推理中，眉眼输出峰值约 0.001–0.002，下颌约 0.20–0.24。相反，资产的眉、眼、鼻、面颊形变数据非零；固定头部逐通道强制驱动时，名字对应的 GPU 权重和局部画面均有变化。此前的口型为主现象主要来自模型上半脸输出弱，加上表情层过于简单，不是资产只有嘴部通道。

现将神经模型用于口型与发音动作，LLM 的同轮情感用于协调眉、眼睑、鼻翼、面颊和嘴角。发音所需的下颌、闭唇、漏斗嘴、撅嘴等通道保留音频值；明确情感时限制其他音频表情残差，避免无条件正向叠加覆盖情感意图。普通中性对话也会根据本地 PCM 相对 RMS，加入低幅、限频、平滑衰减的眉眼重音动作；它不预测情感，也不把小噪声放大成表情。闭眼时压低同侧睁眼与眯眼分量，避免睁眼姿态抵消眨眼。

这些是本地规则和能量控制，未增加 LLM 请求或 GPU 服务；不等同于训练好的整脸声学情绪生成、精确 FACS 强度控制或物理肌肉仿真。七类姿态仍需在每个新角色资产上校准，不能把通道齐全或自动测试通过等同于自然度验收。

### 眉额覆盖与逐部位调节

工具可用的首轮现也强制 JSON 输出，避免模型只口头描述动作而漏发情感元数据；显式表情演示采用相应类别与 0.85–1 的强度，日常聊天仍使用适度情感。普通说话的自动眉部节奏幅度已提高；这不增加推理次数或音频等待。

右上角“部位调节”提供眉毛／额头、眼睑／视线、面颊／鼻翼、嘴唇／嘴角、下颌／舌全部 52 个标准通道入口，按实际资产字典启用。当前形象有 51 个有效通道，缺失 `tongueOut`，相应控件禁用。眉部五通道可独立调节，也可使用抬眉、提内眉、皱眉快捷动作；显示值取自渲染器送入高斯模型的权重，不是 AU 检测或物理肌肉测量。

手动只接管已调通道，其余通道继续自动；恢复自动、关闭面板、更换角色或形象会释放接管。眼睑、嘴部的直接调节属于动作检查，会覆盖该通道的自动眨眼或口型。读数仅在面板打开时每 200ms 更新，不发模型请求。

该资产的眉部形变会带动中下额头，但上额头几何响应显著较弱。现有模型／渲染链没有独立的动态额头皱纹控制；提高眉部权重不会自动补出真实皱纹。完整眉额外观仍需要更丰富的纠正形变与动态外观能力，不能把增加滑杆当成这一能力已完成。

`audio_video` 记录须同时满足有声 AudioContext 播放已观察到、匹配的面部参数已提交渲染、PTS 差在 100ms 内。真实麦克风、云端延迟和长会话还应分别测量；单次文本起播不能证明“说完后 3 秒”的语音指标。

## 语音短答约束

语音系统提示词要求面对面交谈式短答：默认 1–2 句、约 20–60 字，正文最多 80 字，只讲当前问题最重要的一点；复杂话题分轮展开，不主动变成长篇科普、列表或演讲。用户明确要求详细说明时，每次仍最多 3 句、120 字。字符约束针对 speech 可播报正文，不包含表情 JSON 与提交标记。工具调用和结构化输出协议保持一致。

本轮延迟面板与短答版本验证（2026-10-30）：Mac Chromium 1600×1000 和 1280×800，合成录音到有声播放 2714ms、音画确认 2719ms；首块 Avatar 367ms、首段 TTS 303ms、首个可播报正文 LLM 786ms。数字与实际播放上报一致，后续音频不改写首项，新会话恢复“—”；桌面底栏无溢出，浏览器相关错误为零。该结果是一次观测，不是 P95。前端 30 项检查、Go race/vet、构建通过。

## 七类情感与情感 TTS 验证（2026-10-30）

TTS 改用 `qwen-audio-3.1-tts-flash`、`longanhuan_v3.1`、24 kHz PCM。LLM 同一条结构化回复输出基础七类情感与 0–1 强度；本地将这份状态同时交给脸部混合器和 TTS 的 `instruction`。原 Qwen3-TTS-Realtime 协议继续兼容。连接提前准备，情感确定后才启动任务；每段新 UUID，完成后复用连接，取消关闭连接，不重放部分音频。

## 眉眼增强与多轮表情修复（2026-10-30）

已确认 LLM 情绪能传到眉眼，但旧映射的中等强度偏弱，例如 happy/0.6 的外眉仅 0.30、眯眼 0.36。现提高六类非中性姿态的眉眼、面颊与嘴角幅度，以保持 0/1 端点与单调性的 `s × (1.7 − 0.7s)` 增强中等强度。发音下颌、闭唇、漏斗嘴、撅嘴等仍完全沿用音频值，眨眼继续抑制相应睁眼通道；零强度时 PAD 不再留下表情残量。
