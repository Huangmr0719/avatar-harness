# 实时对话：分段与 TTS 连接流水线

实施日期：2026-10-29。目标是一对一、可打断的数字人语音对话，不增加直播能力，不更换 DeepSeek／Qwen ASR／TTS 配置。

## 已落地

```text
最终 ASR → LLM 逐词生成 → 正文提交门 → 分段器 → 并发 TTS → 保序 PCM → 浏览器播放
             │                                 ↑
             └──── 同时准备各 TTS 工作通道的连接 ────┘
```

### 连接准备不再串在首段后面

`internal/provider/tts_stream.go` 新增一轮对话内的合成工作通道。创建 `Speech` 时异步建立、配置百炼连接，与 LLM 请求重叠。后续分段重复 `input_text_buffer.append`／`commit`，以 `response.done` 结束本段，不逐段结束会话并重连。

默认两条通道各有自己的连接，不能混用音频响应。轮次完成、打断或连接异常都会关闭对应连接；不跨会话／轮次复用，也不自动重播已输出部分的文本。一次性 provider 调用和其他 provider 的既有协议保持兼容。

### 首段短切，后续逐步增大

`internal/runtime/speech.go` 的分段器优先使用标点；首段、第二段、后续段分别采用约 24／48／96 字符的长度目标。新增独立计时阶段：首段默认 180ms、后续默认 400ms，从这一段首次缓冲文字开始计，不随每个 token 重置。

到达预算时，只有已有足够内容和可切分边界才提交：首段至少约 8 个中文字／4 个英文词，后续约 12 个中文字／6 个英文词。未结束的英文词、数字、时间和过短片段继续等待。模型结束会刷新剩余文字。参数为 `limits.tts_first_chunk_ms`／`tts_chunk_ms`；旧配置自动加载默认值，无需重写用户配置。

### 并行生成，按序输出

待合成队列容量等于通道数，每段的音频包队列容量为 4；后段可以先合成，但只有前段音频结束后才能发出。PCM PTS 始终按实际样本数累积。队列满时反压上游，停止操作可以取消队列等待、准备中的连接和正在合成的响应。

`<speak/>` 仍是正文提交门槛，计时器不会让工具决策草稿进入 TTS。最终 ASR 确认与 Avatar 先准备动作、再按共同 PTS 输出的同步约定保留；本次没有把临时转录当成正式请求，也没有用先播音频冒充音画同步优化。

## 可重复的本地前后对照

`BenchmarkSpeechPipelineFirstAudio` 使用本地 WebSocket 协议夹具：固定 120ms 模型首段等待、40ms 连接准备、一条合成通道、三个文本段；不含真实模型推理或浏览器播放。改动前后各运行 5 次：

| 指标 | 改动前 | 改动后 |
|---|---:|---:|
| 首个音频包进入输出通道 | 166.6ms | 121.0ms |
| 每轮 WebSocket 建连数 | 3 | 1 |
| 整轮控制流完成均值 | 260.1ms | 121.2ms |

这验证了连接准备被移到模型等待期间、三段不再重复建连，不是云端对话的提速比例。原始配置与数字见 [performance-pipeline-local.json](performance-pipeline-local.json)。

复核命令：

```bash
./scripts/go test ./internal/runtime -run '^$' -bench '^BenchmarkSpeechPipelineFirstAudio$' -benchtime=5x -count=1
```
